Conversation archive: every agent turn, as Vortex in R2

Design record · decided 2026-11-09 · CLIProxyAPI fork local/maintained + new repo cliproxyapi-archiver

Record every request and response that passes through the proxy as an audit log you own, store it in Vortex files in a Cloudflare R2 bucket, and query it with DataFusion. The proxy stays dumb and fast: it writes raw records to a local ring-buffered write-ahead log. A Rust daemon does the parsing, deduplication, Vortex writing, upload and querying.

Decisions

Scope
Proxy traffic only. Every agent routed through the proxy, provider-agnostic. Harness-local transcripts are out.
Fidelity
Raw bodies as the agent sent and received them. Structure is recovered by byte-exact slicing, never by re-serializing, so parsing is additive and the original bytes always come back.
Stack
DataFusion is the query engine; Vortex writing and querying live in Rust. Go has no production-grade Vortex writer.
Boundary
Proxy appends raw frames to a local WAL; a separate Rust archiver drains it to R2. No links or dedupe in the WAL; no cgo; no network in the proxy hot path.
Dedupe
In the Rust archiver: slice system, tools and each message, hash with blake3, store each unique slice once in a blobs table, store the turn as skeleton + ordered hashes. Raw fallback when the splitter declines.
WAL
Ring buffer of 16 × 64 MB zstd segments (1 GB). Segments roll at 64 MB or 15 minutes with fsync. When full, the proxy drops the oldest segment and counts it. The archiver drains oldest-first, newest-first above a high-water mark of 12 segments.
R2 access
Static R2 API token scoped to one bucket, object read/write only, stored in a new archive section of the proxy config and editable in the management panel. The archiver reads the same config.
Encryption
R2 SSE-C with an AES-256 key we hold, in the same config section; Cloudflare keeps no copy. Switch to Vortex segment encryption when vortex-data/vortex#10968 ships; the schema does not change. The proxy's own access key is never archived, only its SHA-256.
Code
Go capture and WAL writer in the proxy fork. Rust archiver in a new repo, tomsanbear/cliproxyapi-archiver, with its own ticketsplease board. The WAL frame spec is versioned in both repos with shared golden fixtures.
Failure
The proxy never blocks a request for the archive. Drops are counted and shown in the management panel with ring depth and last successful upload.

Pipeline

In the proxy

  • Inbound body is already captured after auth by CaptureAuthenticatedRequestBody (internal/api/middleware/request_logging.go:127). We reuse that capture and never read the body twice.
  • Downstream response: the existing request-log path drops stream chunks when its 100-slot channel fills (response_writer.go:119). The archive taps the synchronous writers instead, ForwardStream.WriteChunk and forwardClaudeStreamWithState, which see every byte including synthesized error frames, and buffers in memory per request.
  • Metadata comes from the usage record (sdk/cliproxy/usage/manager.go:26): session and parent session, account id, provider, model, status, latency, TTFT, input/output tokens, cache read and creation tokens with the 5m/1h split. A usage plugin joins it to the captured bodies on the gin request id (TraceID), and a turn record is emitted once both halves are present or the request finishes with an error.
  • WAL format: a directory of numbered segment files (seg-000000123.zst), each a zstd stream of length-prefixed frames, one frame per turn. Segments roll at 64 MB or 15 minutes with fsync on roll. A crash leaves at most a truncated tail frame, which the reader skips. The directory listing is the only index. The WAL is a new archive config section and a runtime component shaped like sdk/cliproxy/pprof_server.go: started in Service.Run, flushed in Shutdown, hot-reloadable.
  • Ring buffer: at most 16 completed segments. On roll, if 16 exist, the proxy unlinks the lowest-numbered one and counts the drop. Unlinking an open file is safe: an archiver mid-read finishes from its descriptor and the data is archived anyway. Both sides ignore ENOENT; there is one writer and one reader, so no locking.
  • Hot path cost: one memory copy of a body the proxy already holds, then a buffered file append. Bounded by a size cap per record (same 32 MiB as request-log). A write error drops the record with a counter; no request ever waits on the archive.

Why the raw volume is large, and what to do about it

Every API call resends the whole conversation. Two things repeat on each call: the static prefix (Claude Code's system prompt plus tool schemas, roughly 50–80 KB), and the growing message history. Each tool call is its own round trip, so a session with 200 tool calls makes 200 requests, and the last one carries everything before it. The new bytes per turn are one assistant message and one tool result, usually 1–10 KB, plus the response.

Across the ~17k calls a week the logs show, that is roughly 2–8 GB a week raw before compression, against perhaps 100–200 MB of genuinely new content. Vortex's column encodings will not recover the difference reliably: they work within a column chunk, and these are multi-kilobyte repeats scattered across rows and files. The fix is a small amount of structural parsing.

Structural, byte-exact dedupe

  1. Tokenize each request body only far enough to find the boundaries of the parts that repeat: for the Claude format system, tools and each messages[i]; for OpenAI chat messages[i] and tools; for Responses instructions and input[i]; for Gemini systemInstruction, tools and contents[i].
  2. Slice the original bytes at those boundaries. Nothing is re-serialized or canonicalized.
  3. Hash each slice (blake3). Store each unique slice once in a blobs table. Store the turn as the body skeleton plus the ordered list of hashes, so the exact original bytes come back by concatenation.
  4. Anything the splitter cannot handle, such as an unknown format, malformed JSON or a non-JSON body, is stored whole as raw. No interpretation of content means no parser gap can lose data.
  5. Responses are unique per turn and stay raw.

This also produces the per-message table you would want for analysis anyway, which is a better "parsed subset" than hand-picked columns.

Why the dedupe runs in the archiver

Deduplication is stateful: whoever does it must know which blobs are already durably stored. Putting it in the proxy would create a consistency dependency from R2 back into the proxy's index; the raw WAL avoids that at the cost of local disk, which the ring bounds at 1 GB.

Schema evolution: new columns are added as nullable; DataFusion merges file schemas on read, so old files simply have nulls. A type change is a new column name, never a redefinition, because Schema::try_merge rejects type conflicts. schema_version on each row records which writer produced it.

Sizing: one turns file and one blobs file per hour of activity, so a day is at most 48 files and a year a few thousand; DataFusion's listing handles that without a catalog. If it ever matters, Vortex is heading into Iceberg and the files move as-is.

Querying

The archiver binary doubles as the query tool: cliproxyapi-archiver query 'SELECT …' registers turns and blobs as DataFusion ListingTables over the R2 prefix via vortex-datafusion, with a reassemble(request_skeleton, request_parts) scalar UDF that returns the original bytes. The S3 client carries the SSE-C key, so reads are transparent. A local cache of recently read files avoids re-fetching. Because it is plain DataFusion, anything else you write in Rust can embed the same SessionContext.

Encryption

Vortex's own encryption is designed but not shipped: the file footer reserves encryption_specs and a per-segment index, documented as unused, and the implementation is PR #10968 (segment-level AES-GCM, KeyRetriever), open as of 2026-11-09 against 0.93.0. Until it lands, the archive uses R2 server-side encryption with a customer-provided AES-256 key (SSE-C): every put, get and multipart step carries the key, Cloudflare stores no recoverable copy, and object_store 0.13 already supports it (sse_customer_key_base64). Compression, dedupe and schema are unaffected, so moving to Vortex-native encryption later is a writer and reader option, not a migration.

Work breakdown

Each row is a ticketsplease ticket: 1–3 in the proxy repo, 4–7 in cliproxyapi-archiver, 8–9 in both.

  1. WAL frame spec (both repos): frame layout, header fields, segment naming and ring rules, zstd framing, truncated-tail rule, version byte. Golden fixtures shared by the Go writer and Rust reader.
  2. Proxy capture (claude/executor, usage, new archive scope): lossless response tap, request-id join of body and usage record, turn assembly, credential stripping, size cap.
  3. Proxy WAL writer + config: archive config section (spool dir, ring size, R2 endpoint/bucket/prefix/token, SSE-C key), ring-buffered segment writer with start/flush/reload, drop counters, management-panel settings and status.
  4. Archiver: WAL reader: segment discovery, frame decode, oldest-first drain with newest-first above high-water, delete after confirmed upload.
  5. Archiver: splitter: byte-exact structural slicing per format, blake3, skeleton encoding, raw fallback, reassembly, golden tests from real captured bodies.
  6. Archiver: Vortex writer + upload: Arrow schema, hourly roll by row timestamp, object_store S3 client against R2 with SSE-C, idempotent uploads, manifest.
  7. Archiver: query CLI: DataFusion context, ListingTables, reassemble UDF, a few saved queries (turns per session, cache hit rate per account, cost per day).
  8. Deployment: launchd service for the archiver, log rotation, a health check in the management panel showing spool depth and last upload time.
  9. Verification: run both for a day, then prove round-trip: for a sample of request ids, reassemble equals the bytes the proxy logged; row counts match proxy request counts; cache hit rate from the archive matches the measurement ticket already planned.

One thing this also buys: the measure-cache-hit-rate ticket on the board becomes a query over this archive rather than a separate logging feature.

Order of work

The WAL frame spec first, since both sides build against it. Then the proxy capture and writer, so real traffic starts filling the ring while the archiver is built. Then the archiver reader, splitter and writer, verified against the frames the proxy has already produced. The query CLI and deployment last.
